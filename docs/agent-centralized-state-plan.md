# Agent 状态集中管理与按需认证方案

时间：2026-11-18（Asia/Shanghai）  
状态：已实施。当前行为与部署参数见 `docs/architecture.md`、`docs/deployment.md`；下文保留设计依据。

## 1. 目标与范围

将 Controller 作为节点配置、项目配置、任务及结果的唯一持久化来源，继续使用 JSON，不增加数据库依赖。Agent 主动连接 Controller，只查询本机运行状态、接收操作并执行，不保存应用身份文件、任务文件和仓库凭据。

仓库认证每次随实际需要使用的操作下发，仅限该操作需要且节点已获授权的仓库。普通状态查询、启停、删除和清理操作不携带仓库凭据。

保留 standalone 的本机管理方式；本方案调整 Controller/Agent 模式，不要求兼容旧节点协议和旧 Agent 数据。

这里的“集中持久化”针对 Poke 管理状态。Docker 镜像、容器、数据卷及 bind mount 业务文件仍属于执行主机，不能通过迁移 JSON 变成 Controller 本地文件。

## 2. 当前实现与差距

- Controller 已保存节点、注册状态、仓库授权和任务，仓库秘密与公开配置分开保存。
- Agent 当前保存 `identity.json` 和任务文件，使用本地记录去重、重启恢复和补报结果。
- 仓库凭据已通过协议 `Request.Registries` 传入操作上下文，不写入任务记录。
- 镜像拉取通常按域名筛选认证；项目操作、容器更新等路径可能先携带该节点全部获授权仓库，再由 Agent 筛选，范围过大。
- Compose 源文件目前由 Agent 管理；Compose CLI 为认证生成临时 `DOCKER_CONFIG`，异常退出后依赖下次启动清理。

主要改动是状态归属、节点启动认证、任务确认协议、项目源文件归属，以及凭据的精确选择，并非重新实现一套全量配置推送。

## 3. 数据归属

| 数据 | Controller | Agent |
| --- | --- | --- |
| 节点信息、仓库授权 | JSON 持久化 | 当前会话内使用 |
| 节点认证摘要、撤销状态 | JSON 持久化 | 从启动环境读取长期节点凭据 |
| 仓库账号、密码、Token | 私有 JSON，仅 Controller 保存 | 单次操作内存；Compose CLI 使用临时认证目录 |
| 项目源配置、版本 | 按节点和项目持久化，操作引用确定版本 | 执行时获取相应版本，生成运行材料 |
| 任务状态、操作参数、执行结果 | JSON 持久化，敏感输入独立保护 | 当前进程内队列、去重表及待确认结果 |
| 主机、容器、镜像、网络、存储卷状态 | 按需获取，可短期缓存并注明采样时间 | 实时查询 Docker |
| Docker 数据与 bind mount 文件 | 不接管 | 仍由 Docker 主机管理 |

Controller 需要保存足够的非认证操作参数和项目版本，便于审计及人工确认；仓库凭据不进入任务 JSON。Compose 内容可能包含业务秘密，源配置和操作参数仍按私有文件处理，不能当作可公开日志。

Controller 写入继续采用 `0600`、原子替换、文件与目录同步及目录锁；损坏时拒绝覆盖启动。

## 4. 长期环境变量身份与防重复

### 4.1 节点身份

按已确认的方向，Agent 使用长期环境变量认证，不再通过临时注册生成本地身份文件：

1. 管理员创建节点，Controller 生成稳定的 `POKE_NODE_ID` 和随机 `POKE_NODE_TOKEN`。Token 明文仅展示一次，Controller 保存绑定该节点 ID 的摘要。
2. Agent 使用 `POKE_CONTROLLER_URL`、`POKE_NODE_ID`、`POKE_NODE_TOKEN` 启动并主动建立 TLS 连接。Token 无 10 分钟有效期，持续有效直到轮换或撤销。
3. ID 存在、Token 与该 ID 绑定的摘要匹配且节点未撤销，即视为同一个逻辑节点。进程重启、连接重建、IP 或主机名称变化均不创建新节点记录。
4. 未知 ID、错误 Token、拿其他节点的 Token 配当前 ID、已撤销身份均拒绝连接；连接请求不自动创建节点，也不覆盖已有节点信息。
5. 轮换 Token 保留原节点 ID、项目和任务关联，递增凭据版本，关闭旧会话；旧 Token 立即拒绝后续连接。Token 遗失时重新生成，不能从摘要恢复明文。

`POKE_NODE_TOKEN` 必须长期保留，重启时不能删除；`POKE_ENROLLMENT_TOKEN` 和临时注册步骤在新方案中移除，不做旧方案兼容。节点身份匹配不代表允许两个 Agent 同时执行任务。

TLS 的私有 CA 文件属于部署输入，可按需挂载，不属于 Agent 自己写出的状态。客户端 IP、主机名、Docker 信息只作诊断，不作为身份依据。

### 4.2 同一节点只允许一个活动实例

每次 Agent 进程启动生成随机内存 `boot_id`，同一进程重连保持不变；每条连接由 Controller 分配新的 `session_id` 和递增 `session_epoch`。`boot_id` 区分进程，不能替代 ID + Token 认证。

| 已有状态 | 新连接 | 处理 |
| --- | --- | --- |
| 没有有效实例租约 | ID + Token 正确 | 原子占用该节点，完成握手后上线，不新增节点记录 |
| 已有同一 `boot_id` | 原进程重连 | 原子替换连接、递增会话代数，关闭旧连接；对账已有任务，不重复执行 |
| 已有不同 `boot_id` 且租约有效 | 第二个实例使用相同 ID + Token | 拒绝并返回 `NODE_ALREADY_CONNECTED`，保留原实例，不反复踢线 |
| 原连接断开但租约未到期 | 不同 `boot_id` | 返回 `NODE_RECONNECT_PENDING`，等待原实例恢复或租约过期 |
| 租约已到期 | 不同 `boot_id` | 允许成为同一节点的新实例；旧实例未结任务先进入结果待确认，禁止冲突修改 |
| 凭据错误或节点已撤销 | 任意 `boot_id` | 返回认证错误，不抢占会话、不创建节点 |

Controller 对同一 `node_id` 的认证完成、租约检查、连接占用和会话替换使用同一临界区；多个连接同时到达时只允许一个成功。连接中途握手失败应释放自己的占用，不能留下永久在线状态。

连接关闭回调、结果消息及数据通道都必须校验当前会话标识，旧连接关闭不能删除新连接；过期会话不能领取仓库认证、获取新执行许可或建立终端/日志流。数据通道使用绑定当前控制会话的短期一次性票据。

### 4.3 租约、重启与接管

建议心跳间隔 20 秒、租约 60 秒。Controller 接收有效心跳后持久化续租期限，再向 Agent 确认；Agent 使用本地单调计时记录已确认的保守期限，不能自行延长租约，重启不能继承旧期限。租约过期立即停止接收新修改，尽力取消尚未完成的执行。

Controller 用 JSON 保存租约所有者 `boot_id`、凭据版本、会话代数及到期时间。Controller 自身重启后，未到期租约先进入恢复状态：原实例认证并对账后恢复，新实例等待租约释放或过期，不能因内存会话表清空就同时放行。

续租采用先落盘再确认；落盘失败停止续租及新任务许可。租约只能限制新执行，不保证中断已经交给 Docker 的操作，也不能保证消除跨进程副作用。

正常退出时，Agent 停止接单、处理或报告在途任务后发送释放请求；Controller 持久化释放后，新实例可立即连接。无法确认旧进程结束时，不依据浏览器点击“重新连接”直接抢占。首版不提供无条件自动踢线接管；人工解除冲突需明确展示旧任务，并确认旧实例已停止及实际资源状态。

有已许可但未结束的旧任务时，即使允许新实例上线，也只允许查询和对账；先按节点冻结新修改，明确解决 `unknown` 任务后再恢复。不能仅凭租约到期就认定旧 Docker 操作已经停止。

### 4.4 重复连接的提示与重试

Agent 日志显示节点 ID、错误码及重试间隔，不打印 Token。重复实例按带随机抖动的退避重试，避免持续争抢；认证失败提示检查环境变量，不能自动生成新 ID 或注册新节点。

Controller 页面保留一条节点记录，展示重复连接尝试、最近时间、当前实例启动标识及连接状态；冲突尝试不将正常在线节点改成离线，也不覆盖其名称或资源快照。诊断记录限制频率和保留数量，不持久保存 Token。

## 5. 获取数据与执行操作

Agent 不启动 HTTP 服务，保留主动控制连接与独立数据连接；Controller 不需要直连 Agent 地址。

- 列表、详情、日志及终端：Controller 经现有数据通道按需查询，Agent 不将响应写盘。
- 项目编辑及查看源配置：浏览器访问 Controller 保存的源文件，不依赖节点在线；页面区分“配置版本”和“节点当前实际状态”。
- 修改操作：Controller 先保存任务和引用版本，再下发。Agent 不定期拉取整份设置或仓库列表。
- 新建、修改和删除受管项目：先形成 Controller 上的待执行版本或删除意图，确认执行结果后再更新已部署版本或完成删除；失败保留源配置及诊断，不提前宣称部署成功。
- 外部创建的 Compose 项目作为发现资源展示，不自动变为 Controller 管理项目；显式导入后才建立源配置和版本。

项目以 `node_id + project_id + revision` 隔离；下发携带任务 ID、会话 ID、目标资源、配置版本/摘要和执行期限。不能只用可修改的项目名称关联源配置。

## 6. 仓库认证按需下发

凭据在任务即将执行时准备，不在入队时保存快照，避免等待期间授权和密码已经变更。

1. Controller 保存任务，Agent 排队；轮到执行时，Agent 发送准备请求。
2. 确定本次需要的镜像域名：单镜像拉取/检测直接解析镜像名；容器更新由 Agent 查询实际镜像；Compose 按确定版本、操作和目标服务解析镜像。
3. Compose 渲染需要本机环境时，由 Agent 使用固定版本、固定输入执行 `compose config --images`，在现有出站连接上返回域名集合和配置摘要。Controller 校验任务、当前会话、授权和范围后再返回执行许可。
4. Controller 计算“本次需要的仓库 ∩ 节点授权 ∩ 已保存的认证”，只随本次执行许可返回匹配凭据。Agent 不能通过提供任意域名读取全局仓库认证。
5. 凭据与 `task_id/request_id`、`session_id`、准备阶段摘要及领取次数关联；Agent 校验后只注入该次上下文。准备阶段与执行阶段输入不得变更。
6. 任务结束、取消或超时后释放上下文和临时材料。重连不补发旧认证，新操作重新检查授权并读取最新凭据。

| 操作 | 认证范围 |
| --- | --- |
| 普通列表、详情、日志、终端 | 无 |
| 容器启停、删除，镜像/卷清理 | 无 |
| 镜像拉取、更新检测 | 对应镜像仓库 |
| 容器更新 | 实际拉取的镜像仓库 |
| Compose 部署、拉取、更新 | 本次目标服务涉及的镜像仓库 |
| Compose 停止、删除 | 默认无，按实际执行命令判断 |

缺少认证不提前判定操作失败，公开镜像仍允许匿名访问。仓库拒绝时沿用现有结构化错误，区分缺少认证、认证失败、镜像缺失、连接及仓库异常。

Docker SDK 直接使用内存认证；Compose CLI 的 `DOCKER_CONFIG` 写到 Agent 私有临时目录，容器部署优先使用 tmpfs，并在完成后删除。临时目录不得进入 `/poke` 数据卷，不调用持久 `docker login`。未配置 tmpfs 时不能宣称凭据绝不接触磁盘。已下发的仓库密码本身不会因任务超时而失效；这里限制的是分发范围与生命周期，不是把仓库密码转换成一次性凭据。

## 7. 不落盘的任务协议

移除 Agent 任务文件后，不能继续依赖“本地落盘即确认接收”。改为 Controller 持久确认执行许可：

1. Controller 保存 `queued`，Agent 仅在内存入队并去重。
2. Agent 准备执行时发送 `ready`，Controller 校验当前会话和任务状态，持久化执行许可后返回 `execute`，并附本次必要凭据。
3. Agent 收到许可后开始执行，同一 Agent 内修改操作继续串行，保持队列上限、执行超时和取消机制。
4. Agent 将结果保留在内存并报告；Controller 保存终态后返回 `ack`。同一进程断线重连可以补报未确认结果；收到确认后释放。
5. 所有任务消息绑定 `node_id + boot_id + session_epoch`，执行许可绑定任务 ID 和唯一许可 ID。Agent 内存按任务 ID 去重，Controller 原子判断状态；重复 `ready` 不产生第二份许可，重复 `execute` 不重新调用 Docker，重复结果只确认同一终态。
6. 同一进程重连后，Controller 根据当前任务和实例对账；不重新下发旧执行许可。新进程没有内存去重记录，已可能执行的任务转为 `unknown`，不得通过重新连接自动再执行。旧会话消息拒绝，但原进程可在新会话认证并通过任务归属检查后补报结果。

状态建议为：`queued → prepared → execution_granted → succeeded / failed / cancelled / unknown`。是否真正开始执行可能不可观测：**执行许可一旦可能送达，断线或崩溃后就不能自动重新投递该任务。**

只有 Controller 能证明执行许可从未发出的任务才允许重新排队。许可发送失败但无法确认是否送达，也进入 `unknown`。Controller 重启对所有未结束的已许可任务先做对账；节点进程重启后，不再声称能恢复丢失的本地结果。

结果待确认时展示目标资源和操作信息，允许查询实际状态及人工创建新任务；资源已达到目标不代表原任务的每个步骤都成功。不承诺跨进程严格一次执行。

未知任务涉及的节点/项目应暂停冲突修改，直到完成对账或人工解除。会话编号不能中断已发给 Docker 的请求，不能只靠新会话替换就认定旧副作用已停止。

## 8. Compose 运行材料与本机目录

Controller 保存唯一源配置；Agent 执行时使用任务引用的确定版本。Compose CLI 仍需要工作目录，不能将 Controller 文件路径直接交给远端 Docker。

- Compose 文件和可重新生成的配置作为运行材料下发，不作为 Agent 的管理数据真源；不保存仓库密码。
- 使用固定项目名和工作路径，避免不同临时目录生成不同项目身份或改变相对路径解析。
- 业务目录如 `/poke/projects/<项目>/data` 仍位于执行主机，保留相同宿主机/容器路径映射，不迁移或自动清理。
- 被容器作为文件 bind mount 引用的配置需要稳定的宿主机文件，不能执行后直接删掉或替换 inode 后假定运行中的容器已经更新；配置变更要配合明确的容器重建策略。
- 只含内联 Compose 的项目可以使用临时运行目录，但必须固定项目名，并将所有相对 bind 路径解析到稳定的宿主机工作路径。
- 本地 build context、`env_file`、`include`、`extends` 等外部输入不得静默丢失；首版明确拒绝未受管依赖并返回说明。完整支持需后续增加受限文件包及路径校验，继续禁止符号链接越界。

因此 Agent 可以不保留身份/任务/仓库 JSON，但不应承诺整台 Agent 主机无任何持久文件，也不能立即删除现有 `/poke:/poke` 挂载。若要求完全取消 Agent 文件目录，需限制为不依赖宿主机文件的镜像/容器操作，并进一步收窄 Compose 能力。

## 9. 实施顺序

1. 协议与启动：提升协议版本，分离 Controller JSON Store 与 Agent 内存运行状态，改用长期节点 Token，落实节点 ID 唯一性和摘要认证；Agent 启动不初始化本地配置与任务存储。
2. Controller 项目源配置：增加按节点、项目及版本隔离的存储和接口，区分草稿、已部署版本与实际运行状态。
3. 任务协议：实现执行准备、持久执行许可、节点原子占用、持久租约、会话/启动标识、结果确认及未知状态；禁止重复实例并行执行及不确定任务自动重放。
4. 按需认证：统一镜像解析、授权检查与任务上下文，删除广泛携带全节点凭据的路径，Compose 认证改用临时目录。
5. 页面和部署：显示未知任务、配置版本及节点新启动状态；更新节点凭据展示、Compose 示例、README 与部署文档。
6. 在明确授权后实施，不迁移旧 Agent 状态，不自动删除业务目录；Controller/Agent 需要成套升级。

## 10. 验收

- Agent 无 `identity.json`、任务 JSON、仓库配置写入；保留长期节点 Token，重启仍识别为原节点，不新增记录。
- 并发启动两个相同 ID + Token 的实例，只能一个上线执行；不同 ID 复用 Token、错误 Token 和已撤销 Token 均被拒绝。
- 同进程重连不会重复执行任务或被旧连接清理误删；第二实例不会反复踢掉原实例。
- Controller 重启仍遵守原有效租约；租约到期、Token 轮换和正常释放按明确规则接管，有未知任务时冻结修改。
- 重复投递准备、执行和结果消息不产生额外 Docker 调用；新进程无法借重连重放旧任务。
- Controller 不可用时不执行新修改，现有容器继续由 Docker 运行；节点恢复后能查询真实状态。
- 普通查询和不需要拉取的操作不包含认证字段；多仓库 Compose 仅收到实际需要且获授权的凭据。
- 排队后撤销授权或修改密码，执行时采用最新授权及凭据；重连不能重放旧许可。
- 在准备、发许可、执行、报结果及确认各阶段注入断线/进程退出，不重复执行不确定修改。
- Agent 进程退出后无法恢复的任务进入 `unknown`，界面不误报成功或自动重试。
- Controller 重启、身份撤销、重复 Agent 实例、会话替换均有明确处理；覆盖旧实例未停止副作用的情况。
- Compose 相对路径、持久目录及挂载文件行为正确，未支持的外部依赖明确拒绝，路径边界测试保留。
- 认证不写入任务、日志或持久卷；临时认证权限、并发隔离、异常清理及 tmpfs 部署有测试。
- 使用模拟 Docker、协议集成测试和 JSON 存储测试验证，不自动启动服务或构建镜像。

## 11. 已确认方向与剩余边界

已确认：Token 改为长期环境变量；节点 ID 与对应 Token 验证一致即视为同一节点，重启与重连不新增节点记录。

防重复采用：一个节点一个活动实例、同进程可重连、不同进程有效租约内拒绝抢占、Controller 原子占用并持久保存租约、任务执行许可去重、未知结果不自动重放。相同身份可以复制部署配置，但不能作为多副本负载均衡身份并行执行。

长期 `POKE_NODE_TOKEN` 不能在启动后删除。Agent 无任务持久化意味着进程崩溃可能丢失补报结果，仍需接受“结果待确认 + 不自动重放”。Compose 执行主机必需的运行材料与业务文件仍按第 8 节保留。
